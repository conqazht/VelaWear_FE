## Why this matters

The wishlist currently loads one page and then fans out into one product-detail
request for every distinct product. A user with 100 saved products can therefore
trigger roughly 101 requests, delaying the page and multiplying backend work.
Backend BE-009 is responsible for returning a localized product-card summary in
each wishlist item; this plan consumes that contract in one request while
preserving account-scoped caching and optimistic add/remove behavior.

## Current state

- `components/shop/favorites-provider.tsx` owns wishlist loading and conversion
  to storefront `Product` values. At lines 51–82 it first requests 100 wishlist
  rows and then creates a product-detail query per ID:

  ```tsx
  const wishlistsQuery = useWishlistsQuery(
    wishlistUserId,
    { size: 100 },
    isAuthenticated
  );
  // ...
  const wishlistProductQueries = useQueries({
    queries: wishlistProductIds.map((productId) => ({
      queryKey: queryKeys.products.detail(productId, activeLocale),
      queryFn: () => getProduct(productId, activeLocale),
    })),
  });
  ```

- `components/shop/favorites-provider.tsx:84-109` folds all detail-query loading,
  errors and responses back into the provider. `retry()` refetches the list and
  every failed detail request.
- `lib/api/types.ts:252-258` has an optional, unproven nested product:

  ```ts
  export type Wishlist = {
    id: number;
    userId: number;
    productId: number;
    product?: Product;
    createdAt?: string;
  };
  ```

- `lib/api/commerce.ts:122-124` calls `GET /wishlists/me`; the Axios request
  interceptor sends the active locale through `Accept-Language`.
- `lib/queries/commerce.ts:41-50` caches that response through
  `useWishlistsQuery`, while `lib/queries/keys.ts:27-30` keys it by user and
  params but not locale:

  ```ts
  list: (userId: number | undefined, params?: unknown) =>
    ["wishlists", "user", userId ?? "anonymous", params] as const,
  ```

- Storefront conversion must continue to use `mapBackendProduct(product,
  activeLocale)` from `lib/vela-data.ts`; do not invent a second mapper.
- The backend contract is external to this repository. The expected BE-009
  invariant is: each `/wishlists/me` row carries a localized, product-card-ready
  `product` summary for its `productId`, with exactly `id`, localized `slug`,
  localized `name`, localized `description`, `categoryId`, `originalSlug`,
  localized `shortDescription`, `status`, `image`, `thumbnail`, localized
  `categoryName`, `categorySlug`, base `price`, and effective `pricing`. The
  executor must verify this exact merged name/shape before changing frontend
  types; SEO/material/care/full images/color images are intentionally absent.
- BE-009's agreed unavailable-product policy is exact: `/wishlists/me` returns
  only wishlist rows whose product is currently `ACTIVE` and not soft-deleted.
  Missing, `INACTIVE`, or deleted products are filtered by the backend paginated
  query before page metadata is calculated, so `result`, `totalElements`, and
  `totalPages` stay consistent. The backend does not return a null/partial
  summary, fail the whole list, or delete the stored wishlist row; a row may
  reappear if its product becomes active again. The frontend renders only rows
  returned by the list and creates no placeholder or extra lookup.
