## Why this matters

The root client provider currently imports every English and Vietnamese message
module, so authentication, storefront and Management routes all share the whole
runtime catalog. This increases client JavaScript and couples unrelated route
groups whenever a message module changes. This plan preserves one locale source
of truth and one global `TranslationKey` type while loading only core messages at
the root and augmenting them with shop or admin catalogs at nested route layouts.

## Current state

- `lib/i18n/messages/index.ts:1-64` imports 19 message modules and spreads every
  module into both locales:

  ```ts
  import { adminShellMessages } from "./admin-shell";
  // ... 18 more runtime imports
  export const messages = {
    en: { ...adminShellMessages.en, /* every module */ },
    vi: { ...adminShellMessages.vi, /* every module */ },
  } as const;
  export type TranslationKey = keyof (typeof messages)["en"];
  ```

- `components/providers/i18n-provider.tsx:26` imports that aggregate. Its `t`
  callback at lines 110–116 reads `messages[locale][key]`, falls back to English,
  then the key.
- The same provider owns locale persistence and cross-tab synchronization at
  lines 48–107. Nested catalogs must not duplicate those effects.
- `app/layout.tsx:48-59` mounts one root `I18nProvider` around Auth and all route
  groups. `app/(shop)/layout.tsx` currently adds shop chrome only;
  `app/(admin)/layout.tsx` adds Management preferences/auth UI only.
- `lib/i18n.ts` is the locale source of truth. `lib/api-client.ts:119-127` reads
  `getActiveLocale()` for `Accept-Language`; do not change this contract.
- `docs/PROJECT_STATUS.md:131-135` records the required behavior: locale persists
  through localStorage and cookie, synchronizes between tabs, updates document
  language, and controls `Accept-Language`, formatting and locale-aware query keys.
- Root `not-found.tsx` and `error.tsx` use `errors.root*` and `errors.common.*`
  keys from `auth-errors.ts`, so the core catalog must include them.
- Direct imports of individual message modules (for typed keys or non-provider
  utilities) exist and should remain valid. `TranslationKey` is imported as a
  type by error components and must continue to cover all namespaces.

### Step 2: Add an executable catalog audit before splitting

Create `catalog-audit.test.ts`. Import all 19 source catalogs and assert, for each
planned namespace and the global union: EN/VI key parity, no duplicate keys
across namespaces, matching interpolation placeholders, and no missing literal
`t("...")` key found in tracked `.ts`/`.tsx` source. Print finite counts on
failure only. This test is the machine guard against silent raw-key fallbacks.

Use this ownership map unless the merged route inventory proves a key belongs in
a different minimal scope:

- Core: `common`, `auth-errors`.
- Shop: `account`, `customer-activity`, `help`, `sales-checkout`,
  `sales-storefront`, `shopping`, `storefront`, `testimonials`.
- Admin: every `admin-*`, `sales-admin-editor`, `sales-admin-management`.

Document any scope adjustment in the test and PR. A key must have one runtime
owner; duplicate spreading is forbidden.

**Verify**: `pnpm exec vitest run lib/i18n/messages/catalog-audit.test.ts` → all
audit assertions pass on the current catalog before architecture changes.

### Step 3: Build separate catalogs while preserving the global key type

Create `catalog-core.ts`, `catalog-shop.ts` and `catalog-admin.ts` with runtime
imports only for their owned modules. Create `types.ts` with type-only imports
that derive the global `TranslationKey` union and shared catalog dictionary
types without creating runtime imports. Change `index.ts` into a compatibility
type/barrel that does not construct or export the former all-messages runtime
object. Root/runtime consumers must import a concrete catalog module directly,
not a barrel that can pull all namespaces into one chunk.

**Verify**: run these separately. The assertion block exits 0 only when there are
no forbidden runtime aggregate patterns; TypeScript then exits 0.
